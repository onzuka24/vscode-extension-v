# 経緯

## 最初の実装とそのレビュー

最初の実装（`feature/initial-source` ブランチ）は、`package.json` の `contributes.keybindings` に
キーを1つずつ並べる方式でした。`h` を `cursorLeft` に、`x` を自前の `deleteCharacter` コマンドに、
というように、**キーバインドの表がそのまま機能の一覧**になっている構成です。

小さく始めるには自然な出発点でしたが、レビューで次の問題が出ました。

| 症状 | 原因 |
| --- | --- |
| Normal モードで `w` `p` `y` などを打つとバッファに文字が入る | 未バインドのキーは VS Code の通常の入力として素通りする |
| `$` が効かない | `"key": "$"` は VS Code のキー構文として無効。エラーも出ずに無視される |
| ターミナルで `Ctrl+J` が奪われる | `when` 句が `vimLike.mode == normal` だけで、フォーカスを問わない |
| Insert 中に Escape でサジェストを閉じられない | Escape の `when` にウィジェットの除外条件がない |
| `o` / `O` でカーソルが新しい行に移らない | 挿入位置がカーソルの反対側にあり、カーソルが動かない |
| CRLF ファイルに LF が混入する | 改行が `'\n'` ハードコード |
| `dd` が最終行で空行を残す | 最終行には後続の改行がないのに、後続の改行を消そうとしている |

重要なのは、**これらが個別のバグではなかった**ことです。1番目の「Normal モードがモードとして
成立していない」は、キーバインド方式を採る限り原理的に避けられません。`$` の件も、キーバインドに
すべてを載せる以上 VS Code のキー構文の制約をそのまま被ります。`when` 句の漏れも、機能の数だけ
`when` を書く方式では必ず起きます。

つまり、出発点そのものを変える必要がありました。

## 作り直しの方針

`main` に戻り、設計から始め直しました。決めたことは3つです。

### 1. エディター内のキーは `type` コマンドのオーバーライドで受け取る

VS Code は文字入力を `type` コマンドとして発行します。これを乗っ取れば、**割り当てのないキーを
破棄できる**ようになり、初めて Normal モードが「モード」になります。

代償として `type` はウィンドウ全体で1つしか登録できず、扱いを誤ると VS Code 全体で文字が
打てなくなります。そのため「確実に自分のものだと言えない入力はすべて `default:type` へ委譲する」
という方針を徹底しています（Insert モード中、IME の変換結果のような複数文字、出力パネルなど）。

### 2. Vim の文法を1つのパーサで表し、オペレータとモーションを直交させる

`[count]["reg][operator][count]{motion}` という Vim の文法を、そのまま1つのパーサで表現します。

このとき鍵になるのが、`dw`（次の単語の手前で止まる）と `de`（単語の最後の文字まで消す）の違いを
**どこに置くか**です。オペレータ側で場合分けすると、機能を足すたびに `オペレータ数 × モーション数`
の分岐が増えます。そこで区分（exclusive / inclusive / linewise）をモーション自身に持たせ、
オペレータはそれを読むだけにしました。結果、実装量は `オペレータ数 + モーション数` に収まり、
**モーションの追加はテーブルへの1行の追記**で済みます。

### 3. VS Code に依存しないコア層を厚くし、テストをそこに集中させる

エンジンは VS Code を呼びません。「何をすべきか」を `Action` の配列というデータとして返し、
アダプタだけがそれを実行します。これによりエンジンの全挙動が「キーを入れてデータが出る」
テストになります。

```ts
assert.equal(run('hello world', 'dw').text, 'world');
assert.equal(run('hello world', 'de').text, ' world');
```

テストヘルパは実際のアダプタと同じ順序（編集 → モード → カーソル）でエンジンを駆動するので、
テストの記述がそのままエディター上の挙動の説明になります。

## 実装の順序

計画では「`type` の配線を先に通してモードを成立させる」順で進める予定でしたが、実際には
コア層を先に完成させ、アダプタを最後に一度だけ書きました。エンジンの API が固まる前に
アダプタを書くと書き直しになるためです。各段階でテストが緑になる区切りは維持しています。

## 現在の到達点

Normal / Insert / Visual / Visual Line の4モード、カウント接頭辞、`d` `c` `y` と全モーションの
組み合わせ、テキストオブジェクト、名前付きレジスタ、`p` `P` ほかの単独コマンド。
コア約1,700行 + アダプタ約400行、テスト72件。

前回の指摘は、個別に直したのではなく構造の側で解消されています。さらに `$` のような
「黙って無視されるキーバインド」の再発は、`contributes.keybindings` の全キーを VS Code の
有効なキー名と照合する構造テストで防いでいます。

## 未対応

Ex コマンドライン（`:w` `:s/foo/bar/`）、検索（`/` `?` `n` `N`）、`.` の繰り返し、マクロ、マーク。
`u` / `Ctrl+r` は VS Code の取り消し履歴に委譲しているため、取り消しの粒度は Vim と一致しません。
モードはウィンドウ全体で1つで、エディターごとには持ちません。

なお `.` の繰り返しについては、パーサが完成したコマンドをオブジェクトとして組み立てる設計に
してあるため、「直前のコマンドオブジェクトを再実行する」だけで実装できる状態にはなっています。
